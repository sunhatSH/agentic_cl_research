## 2. 两条推理路径（别混）

| 路径 | 谁推理 | 在哪跑 | 调什么模型 | endpoint |
|---|---|---|---|---|
| **A. 训练 actor（正式）** | verl rollout LLM server | 训练集群 GPU | **Qwen3.6-27B**（本地权重） | verl 内部 `LLMServerClient`（不走 HTTP） |
| **B. 沙箱采集 actor（冷启动/对照）** | **沙箱内 hermes** | 腾讯沙箱 Instance | **openai/gpt-5** | `AGENT_MODEL_BASE` = **sufy**（沙箱可达） |

- 路径 A 是**正式训练**：verl 原生 rollout（lightllm）产出 token + logprob，token/logprob 直接进 buffer，不经过沙箱。
- 路径 B 是**冷启动采集 / 远程对照**：hermes 在沙箱里跑 ReAct（调 sufy 模型 + 执行工具），产 trajectory 入 replay buffer 预热。`scripts/sandbox_grpo_collect.py --actor hermes` 走这条。

## 3. 三个开发机侧 Agent（都在开发机跑，直连 sufy）

| Agent | 模型 | 作用 | 配置 |
|---|---|---|---|
| **Observer** | openai/gpt-5-mini @0.0 | 取证：沙箱 before/after diff 为 ground truth，产 ObservationReport | `agents.yaml: observer` |
| **Questioner** | anthropic/claude-sonnet-5 + 轮换池 @0.9 | 模拟用户出 follow-up query | `agents.yaml: questioner.rotation` |
| **Reward/Judge** | anthropic/claude-4.8-opus @0.0 | 三维打分 → reward | `agents.yaml: reward` |

> Observer 默认 `use_llm=False`（确定性取证、零模型调用）；只有需要模型归纳时才调 openai/gpt-5-mini。
> 模型选型单一信源见 [`模型选型.md`](../archive/模型选型.md)；sufy TPM 配额见 [`模型配额申请_sufy.md`](../archive/模型配额申请_sufy.md)。

## 4. 一次 8 路 GRPO 采集的完整流程

```
1. 起 8 个沙箱（同 v2 镜像、同 persona/seed，位级一致起点）
2. 对每个 query（共 N 个，顺序）:
   a. 8 路并行：每个沙箱里 hermes chat -q "<query>"
      → hermes 调模型决策 + 沙箱内执行工具(python/bash/文件)
      → 产 1 条 trajectory (messages + answer)
   b. 开发机 reward judge 对 8 条轨迹打分
   c. GRPO advantage 归一化 + select_winner → winner 固化
   d. sync_to_winner: loser 沙箱状态对齐 winner + history 累加
3. session 结束: destroy 8 沙箱
4. 轨迹落盘 rollouts/grpo/grpo_<actor>.jsonl + manifest.json
```

## 5. reward 公式（与 ClawEval 评测同构）

```
verdict = {completion, safety, robustness}   各 ∈ [0,1]，judge 模型输出
reward  = safety × (0.8·completion + 0.2·robustness)
```
- **completion 锚定沙箱 diff（真实产物）**，不看 actor 自称 → 反 reward-hacking
- safety 乘性门控：不安全直接 0
- judge 全程冻结（跑数周/多实验测遗忘，避免版本漂移）

## 6. 训练侧消费（rollout → buffer → loss）

```
trajectory (messages + token_ids + logprobs + reward + bucket)
   → trajectory_adapter 转成 verl DataProto
   → 9 桶 Replay Buffer（按能力域分桶，桶内淘汰禁跨桶）
   → CL Loss: L_rl + L_kl + L_replay(从 buffer 采) + L_ent
   → verl PPO 更新策略
```

## 6.1 verl 集成：不 fork，外挂注入

verl 0.8.0 pip 安装，不 fork。CL Loss / Buffer 全部外挂注入：

| 问题 | 结论 |
|---|---|
| 是否需要 fork verl？ | **不需要**。verl 提供三层 loss 注入扩展点 |
| Replay Buffer 是否需要改 verl 源码？ | **不需要**。verl 无 experience replay 概念，Buffer 是纯 Python 模块 |

**三个 loss 注入扩展点**（按改动量从小到大）：

1. **`register_policy_loss` 装饰器**（`verl/trainer/ppo/core_algos.py`）：注册表式，`@register_policy_loss("cl_grpo")` + yaml `actor.policy_loss.loss_mode=cl_grpo`。局限：签名无 replay batch 入口。
2. **`engine.train_batch(data, loss_function=...)`**（`verl/workers/engine/base.py:99`）：loss function 作为参数传入，签名为 `my_loss(config, model_output, data, dp_group)`。`data: TensorDict` 是开放容器——replay batch 的 token/logprob/weight 任意字段打包进 `data`。
3. **`actor.set_loss_fn(loss_fn)`**（`verl/workers/engine_workers.py:584`）：worker 层显式注入。

**Buffer 接入方式**（推荐方式 B）：

- **方式 A**：包装成 `torch.utils.data.Sampler`，从 `RayPPOTrainer(train_sampler=YourBucketSampler(...))` 注入。buffer 数据走完整 rollout → advantage → loss 链路。
- **方式 B（推荐）**：在 `cl_loss` 函数内部直接从 buffer 单例 `buffer.sample(batch_size)` 拿旧数据，前向计算 $-\log\pi(a|s) \cdot w$，加到 loss。$L_{replay}$ 是监督回放（SFT-style），不走 advantage。
- **方式 C**：自定义训练入口 `cl_main.py`，每 step 后 `buffer.update()`、之前 `buffer.sample()`。

**唯一风险**：$L_{replay}$ 在同一 step 内对 replay batch 单独前向时的 FSDP / 梯度累积兼容性——需 GPU 实测，但不需 fork（路 A 在 `cl_loss` 内夹带 replay 数据再前向，路 B 先 `engine.infer_batch` 拿 log_prob 再做标量运算）。

**verl 关键源码索引**：

| 功能 | 文件 |
|---|---|
| Policy loss 注册表 | `verl/trainer/ppo/core_algos.py` (`register_policy_loss`) |
| Loss 标准签名 | `verl/workers/utils/losses.py` (`ppo_loss(config, model_output, data, dp_group)`) |
| Engine 顶层接口 | `verl/workers/engine/base.py` (`train_batch(data, loss_function)`) |
| Loss 注入 API | `verl/workers/engine_workers.py` (`ActorRolloutRefWorker.set_loss_fn()`) |
| Trainer 主循环 | `verl/trainer/ppo/ray_trainer.py` (`RayPPOTrainer.fit()`) |
| 自定义 sampler 入口 | `verl/trainer/ppo/ray_trainer.py` (`__init__(train_sampler)`) |
| KL penalty | `verl/trainer/ppo/core_algos.py` (`kl_penalty(logprob, ref_logprob, kl_penalty=...)`) |

**配置项速查**：

| 配置路径 | CL 方案对应 |
|---|---|
| `actor.policy_loss.loss_mode` | 自定义名（如 `cl_grpo`） |
| `actor.entropy_coeff` | $\lambda_4$ = 0.001（固定） |
| `actor.use_kl_loss` / `actor.kl_loss_coef` | true / Phase 2 扫描 0.01–0.10 |
| `actor.kl_loss_type` | reverse |
| `actor_rollout_ref.ref.*` | $\pi_0$ 或 $\pi_{t-1}$ 路径 |
| `actor_rollout_ref.rollout.n` | 8（traj/query） |
| `algorithm.adv_estimator` | grpo |

## 6.5 数据 Pipeline（训练 & 评测，两线）

> 训练数据从 taskspecs 来、评测数据从 ClawEval 来，两条线独立但共享同一套 9 桶定义（`buckets.json`）和同一套 LLM 分类器（`data_pipeline/classify.py`）。

### 6.5.1 训练数据线：taskspec → parquet → buffer → 训练

> 主入口 `scripts/run_cold_start.py`（打标 + 采集两阶段，tqdm 进度条）；
> 底层引擎 `scripts/sandbox_grpo_collect.py`（沙箱生命周期 + hermes + 多轮）。
> 两阶段可分开跑（`--no-collect` 只打标 / `--no-generate` 只采集）或用
> `scripts/run_cold_pipeline.sh` 串跑。依赖 `.venv`（含 e2b SDK）。

```
data/taskspecs/s_xxx_t0/     ← 上游 taskspec 数据（3878 个任务, 已复制到本地）
│  ├── taskspec.yaml         ← seed_query + task_family（无官方 category！）
│  └── files/                ← 工作区文件（采集时上传进沙箱）

│  ═══ Stage 1: LLM 打桶 ═══
│  python scripts/run_cold_start.py --no-collect --classify-workers 32
│    stage_queries():
│      task_family 静态映射 6 种 (file_organize/data_merge→ops, table_process→
│        office, risky_op→safety, process_design→workflow) → 零成本直接打标
│      其余 → data_pipeline/classify.py::classify_query()
│        → sufy gpt-5.4-mini (32 并发) → {bucket}   (sub_bucket 恒 null)
│
▼  datasets/queries.jsonl   ← {"record_id", "queries":[q1,...], "bucket":"ops"}

│  ═══ Stage 2: 多轮轨迹采集（全沙箱闭环, 无 reward/winner） ═══
│  source scripts/load_tencent_env.sh
│  .venv/bin/python scripts/run_cold_start.py \
│      --no-generate --no-classify --num-queries 3878 \
│      --max-concurrent 32 --collect-mode incremental \
│      --max-turns 3 --hermes-max-turns 30 --slot-timeout 900
│    每个 query 一个独立持久沙箱, actor+observer+questioner 多轮:
│      persona = sample_persona()            会话级抽 1 人设
│      K = randint(1, max-turns)             随机轮数(防坍缩)
│      for turn in 1..K:
│        hermes chat -q <query> [--resume sid]   actor 调 sufy, 沙箱执行工具
│                                                 (turn2+ resume 保留对话记忆)
│        observer.observe(沙箱 before/after diff) → report   (state-only, 无judge)
│        questioner.next_query(persona, report, history) → follow-up | <end_session>
│    三重上下文: 沙箱文件持久 + hermes resume 记忆 + questioner 措辞
│    collect-mode: incremental(跳过已成功) | overwrite(全跑) | retry(只跑失败)
│    每 25 条 temp+rename 原子落盘, bucket/persona_name/num_turns 透传
│
▼  rollouts/cold_start/grpo_hermes.jsonl
│  {"query_index", "messages":[多轮对话], "bucket", "persona_name", "num_turns"}

│  ═══ Stage 3: 格式转换 ═══
│  python scripts/trajectory_to_parquet.py \
│      --input rollouts/cold_start/grpo_hermes.jsonl --out-dir datasets
│    取 messages 的 system + 首个 user → prompt; bucket 透传; 98:2 切 train/val
│
▼  datasets/{train,val}.parquet  列: prompt | data_source | extra_info{bucket,...}

│  ═══ warmup（训练前预填 buffer） ═══
│  python scripts/warmup_buffer.py \
│      --in-dir rollouts/cold_start --out buffer_dumps/warmup.sqlite
│    classify() 第一级 traj.get("bucket") 命中(LLM 打的标) → buffer.load @ 训练启动
│
│  ═══ Stage 4: 训练 ═══
│  bash scripts/train.sh configs/phase1/b1.yaml
│    configs/base.yaml: cl.buffer.warmup_path = buffer_dumps/warmup.sqlite
│    _preload_warmup() 加载 → buffer step 0 就有冷启动轨迹
│    每 step: rollout → extract_trajectories_from_batch(bucket 来自 parquet)
│      → buffer.add_trajectory() → buffer.sample() → CL Loss
│
▼  ckpts/b1-step-N/
```

**关键设计：**
- **parquet 只装 prompt**：assistant 回复不落盘，verl 在线重新 rollout（保证 on-policy token+logprob）
- **Stage 2 全沙箱闭环**：模型调用、工具执行、文件读写全在沙箱内；无 reward/winner（那是训练阶段的事）
- **多轮 = actor + observer + questioner**：observer 看沙箱 diff（ground truth）驱动 questioner 出 follow-up；hermes `--resume` 保留自身对话记忆
- **桶标记在 Stage 1**：静态映射 6 种 task_family + LLM 分类其余（taskspec 无官方 category，sub_bucket 留空）
- **增量安全**：`incremental` 模式跳过已成功、只补缺失+失败，原子落盘不覆盖好数据
- **冷启动轨迹 reward=None**，buffer 用默认 priority

### 6.5.2 评测数据线：ClawEval → manifest → 评测

```
ClawEval tasks/             ← ClawEval 官方数据集（300 任务）
│  T*/task.yaml             ← 每个 task 含 category 字段（官方分类！）
│  C*/task.yaml             ← 多轮 user_agent（12条，无静态映射）

│  ═══ 打桶（静态映射 + LLM 补 user_agent） ═══
│  python scripts/build_eval_manifest.py
│    1) 38 个 ClawEval category → 9 桶（CATEGORY_TO_BUCKET 静态表）
│       "finance"/"procurement" → finance
│       "ops"/"operations"/"terminal"/"file_ops" → ops
│       "what"/"knowledge"/"comprehension"/"memory" → qa
│       "coding" → coding  "research"/"synthesis" → research  ...
│       覆盖 183/195 条
│
│    2) user_agent（12条）→ LLM _classify_user_agent()
│       读首轮 prompt，调 data_pipeline/classify.py::classify_query()
│
│    3) 多模态（~105条）→ 排除
│
▼  eval/claweval_manifest.json  （195 条，每条含 task_id/bucket/category/prompt）
│  分布: workflow:56  ops:44  qa:36  finance:20
│        communication:11  office:11  safety:9  research:6  coding:2

│  ═══ 评测 ═══
│  python -m eval.run_eval --ckpt ckpts/b1-step-100
│    → 所有 195 任务统一评测（不按桶顺序，一次跑完）
│    → 按 bucket 分组统计分数 → CL Score + 遗忘率
│    → 越早训练的桶遗忘越严重、权重越大
│
▼  eval/results/<run_id>/report.json
```

**关键设计：**
- **评测桶 = 训练桶**：两线共用 `buckets.json` 的 9 桶定义，口径一致
- **评测打标不用 LLM（除 user_agent）**：ClawEval 自带官方 `category`，直接静态映射
- **训练打标全量 LLM**：taskspec 没有官方 category，只有 `task_family`（11种，和桶不是同一维度）
- **评测一次性跑完**：全桶统一评测、不分阶段，之后换权重方案只重算数学

### 6.5.3 两线对比

| | 训练线 | 评测线 |
|---|---|---|
| 数据源 | taskspecs（3878 任务） | ClawEval（195 纯文本任务） |
| 分类字段 | `task_family`（10种）≠ 桶 | `category`（38种）→ 9 桶 |
| 打桶方式 | **静态映射 6 种 + LLM 分类其余** | **静态映射** + LLM 补 user_agent |
| 打桶脚本 | `run_cold_start.py --no-collect` | `build_eval_manifest.py` |
| 采集 | `run_cold_start.py`（多轮 actor+observer+questioner） | 不采集（评测时在线 rollout） |
| 共同组件 | `data_pipeline/classify.py` + `buckets.json` | 同一套 |
| 产物 | `train.parquet` → verl 训练 | `claweval_manifest.json` → CL Score |
| 时机 | 训练前预填 buffer | 全部训完后一次性评 |
