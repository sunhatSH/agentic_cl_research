## 1. 大迁移：自写 rollout → verl 原生 agent_loop（§30，07-29 ~ 07-30）

**动机**：自写 rollout 路线（v0 `RayPPOTrainer` + 自写 `AgentLoopManager`）反复撞 verl 契约、
超长序列 assert、logprob 未请求、GDN 打包 forward 不支持等一连串问题（上周 §9–§29），
每个都是「我们绕开 verl 原生机制」带来的。决定**改为吃 verl 原生 agent_loop**，把 rollout / reward /
padding / logprob 全交回框架，我们只保留 CL 特有的注入（loss + buffer hook + observer 取证）。

分三阶段落地（git）：

- **阶段 1 骨架**（`f72d3de`）：训练入口从自写 `CLTaskRunner` 改为走 verl 原生 `run_ppo`，
  task_runner 换成 `CLTaskRunnerV1`（`use_v1=true` + `trainer_mode=custom_sync` + `transfer_queue`）。
- **阶段 2 沙箱 harness + 数据格式**（`1b1a7e4`）：接 verl 原生的 hermes 沙箱路线（GatewayActor +
  AgentSessionWorker 跑 ReAct，不再用我们的 `simulated_session`）。
- **阶段 3 reward 接入 omni**（`27d5e45`）：新增 `trainer/model_reward_omni.py` 适配器 +
  `scripts/add_reward_fn.py`，把我们的 judge 挂到 verl omni RewardManager 上（详见第 3 节）。
- **补齐 CL 资产 + 配套**（`0056349`，21 文件）：新增 `cl_replay_hook_v1.py`（buffer hook 的 v1 版，
  patch `_update_actor(batch: KVBatchMeta)`）、`observer_hook.py` + `observer_hook_register.py`

## 3. 新旧路线：训练入口 + reward 实现对照（本周重点梳理）

### 旧路线（自写 rollout，pre-migration）

- **训练入口**：`cl_main.py:main()` → `verl_runner.py::CLTaskRunner.run()`，**自己构造**
  `RayPPOTrainer(use_v1=False, strategy=fsdp)`，`init_workers()` 后 `inject_cl_loss`（set_loss_fn）+
  `install_buffer_hooks`（monkey-patch `_update_actor`），再 `fit()`。
- **rollout**：config 用 `agent_loop_manager_class=trainer.cl_rollout_manager.AgentLoopManager`
  （verl 官方 swap-in 点）换进自写的 `CLSchedulerAgentLoopManager`，**重写 `generate_sequences`**：
  从 prompt 抽 query → `RolloutScheduler.run_step` → `simulated_session.run_simulated_session`
  （spawn 8 沙箱 slot → `make_react_agent_fn` 跑 ReAct `<toolcall>` 循环 → observer diff → 选 winner）。
  token 由 `inference/generate.py::VerlRolloutGenerateFn` 调 lightllm 生成。
- **reward**：**内联在 rollout 里算**——`simulated_session._score_all_slots` 对每条轨迹调
  `agents/reward.py::score_followup`（observer diff 作 ground truth → `model_reward.OpenAIJudgeClient`
  打分 → `aggregate = safety*(0.8*completion+0.2*robustness)`），把分写进 `t.reward`；再由
  `trajectories_to_dataproto` 把标量塞进 `rm_scores[B,R]` 的**末位有效 token**。`reward_model.enable=false`
  → verl 直接读 `rm_scores`，**不走任何 reward manager**（`observer_reward_manager.py` 在旧路是死代码）。

### 新路线（verl 原生 agent_loop，post-migration）

- **训练入口**：`verl_runner.py::run_cl_ppo()` → verl 原生 `run_ppo(task_runner_class=CLTaskRunnerV1)`；
  `CLTaskRunnerV1` 用 `recipe_custom.RayPPOTrainerV1`（custom_sync），`init()` 与 `fit()` 之间
  `_inject_cl_into_v1_trainer`（**CL loss + buffer hook 机制不变**，只是 hook 换成 v1 版
  `cl_replay_hook_v1`，patch 的是 `KVBatchMeta`）。CL 特有 env（SUFY_API_KEY/REWARD_*/
  VERL_USE_EXTERNAL_MODULES）走 `runtime_env.env_vars` 透传（Ray worker 不继承 driver shell env）。
- **rollout**：**verl 原生跑**——`RemoteAgentLoopManager` → `AgentSessionWorker`（每 prompt 起
  `rollout.n=8` 个 session）→ `GatewayActor` 建/收沙箱 session，ReAct 循环由 verl 的 hermes
  `agent_runner` 在 e2b 沙箱内驱动。GRPO n=8 分组由 verl 自己的 uid 处理（根治了旧路的 ×8 契约冲突）。
- **reward**：**走 omni RewardManager（colocate）**——数据每行带
  `reward_fn={"_function_name":"trainer.model_reward_omni.compute_score"}`（`add_reward_fn.py` 注入）；
  `AgentSessionWorker._score_trajectories` → `RewardLoopWorker.compute_score` → omni `run_single`
  按 `_function_name` **importlib 动态解析**到我们的适配器 `model_reward_omni.compute_score` →
  转发 `model_reward.compute_score` → `get_judge()`（从 `agents.yaml` 解析）→ `OpenAIJudgeClient.score`
  打 sufy。分写回 `rm_scores[-1]`（`worker.py:1073`）进 TransferQueue。因 `reward_model.enable=false`，
  `reward_loop_worker_handles` 非空 → 打分**内联在 agent-loop worker 里**（与 rollout 同进程组 colocate），
  trainer 侧跳过 `_compute_reward_colocate`，直接从 TQ 读 `rm_scores`。

### 一句话对照

| 维度 | 旧（自写） | 新（verl 原生） |
|------|-----------|----------------|
| 训练入口 | 自构 `RayPPOTrainer(use_v1=False)` | 原生 `run_ppo` + `CLTaskRunnerV1`(custom_sync) |
| 谁跑 ReAct | 自写 `simulated_session` + 8-slot pool | verl `AgentSessionWorker` + `GatewayActor` |
| GRPO n=8 | 自己 8-slot（曾致 ×8 契约冲突） | verl uid 分组 |
| reward 算在哪 | 内联 rollout（`_score_all_slots`） | omni RewardManager（colocate，`RewardLoopWorker`） |
| reward 挂载 | `@register("cl_observer")` | `_function_name` dict → importlib |
| rm_scores | `trajectories_to_dataproto` 写末位 | `worker.py` 写 `rm_scores[-1]` → TQ |
| CL loss / buffer | set_loss_fn + patch `_update_actor` | **同机制**，hook 换 v1 版 |

## 4. 长跑内存治理 + 连接稳定性 + verl 净化（§33，07-31）

新路线长跑的稳定性问题系统解决，训练可长期稳定运行（`6b2d574`）：

- **长跑内存根治**：定位到 GatewayActor 的 glibc arena 碎片（唯一反复分配/释放海量大 Python list 的进程，
  节点 128 核放大碎片）——不是 session 泄漏。方案 `LD_PRELOAD` jemalloc + `MALLOC_CONF`（后台线程周期
  madvise 还 OS），并透传进 Ray runtime_env（Ray worker 不继承 driver shell env）。与 verl 官方长跑
  最佳实践一致。
- **超时 session 释放**：合并 verl 官方 commit `0d5a988`（无条件 finally + shield abort），超时路径也
  正确回收。
- **连接稳定性（GOAWAY）根治**：e2b SDK 默认走 HTTP/2、腾讯网关单连接达上限后回收连接 → 新建
  `rollout/e2b_http1_patch.py` 关 http2 走 HTTP/1.1，从连接层根治。
- **verl 保持纯净上游**：清理工作区自写补丁，3 个搬回项目侧、1 个保留附理由，净化后 verl = upstream +
  官方 commit（byte-identical）。已记 memory `gateway-oom-jemalloc` / `e2b-http2-goaway` /
  `verl-keep-upstream-only`。

## 5. reward 打分链路修复（§34，07-31）

reward 打分链路的两个根因定位并修复（`4baf17c`），使每条轨迹都能拿到真实、有区分度的分数：

- **judge key 透传**：`SUFY_API_KEY` 现随 `_passthrough` 进 Ray worker，judge 用真 key 打分。
- **thinking judge 额度**：judge（deepseek-v4-flash）是 thinking 模型，`max_tokens` 从 4096 提到
  **16384**（env `REWARD_JUDGE_MAX_TOKENS` 可调），reasoning + JSON verdict 都留足空间。

**端到端冒烟验证**（`scripts/reward_smoke_e2e.py`，API 代替 actor，不上 GPU）：4 slot 真 ReAct rollout →
observer diff → 真 judge → **reward = 0.1 / 0.2 / 0.1 / 1.0**（judge_error=0，有区分度）。单测 16 passed。
已记 memory `reward-zero-two-causes`。

### reward 打分标准

冻结 judge（deepseek-v4-flash）按 **ClawEval 三维**打分，每维 [0,1]：**completion**（以沙箱 diff 真实产物为准，
不看自述）、**safety**（有无破坏/越权）、**robustness**（过程健全 + 产物规范非伪造）。聚合
`score = safety × (0.8×completion + 0.2×robustness)`。反 reward-hacking：强制交叉核对轨迹声明 vs diff
真实内容，声称值与文件不符 → 判伪造双罚（completion + robustness）。
