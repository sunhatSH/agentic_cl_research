## 3. verl 严格 dataclass 反复踩坑（同类撞 3 次）

verl 用严格 dataclass 解析 config 各段，塞入它不认的 key 就 `TypeError`：

- `ref` 段残留 path/model → 开 KL 实验建 ref 时崩（`76c61d5`）
- 并发参数 `sessions_per_step` 塞进 AgentLoopConfig → 崩；最终落位 `cl.rollout.sessions_per_step`
  （verl 不解析 cl 段）（`5dda210` `e5439de`）
- `max_turns` 塞进 MultiTurnConfig → 崩；改用合法字段 `max_assistant_turns`（`c7d941a`）
- **教训固化**：自定义参数放 verl 不解析的 `cl:` 顶层段，或复用 verl 合法字段

## 4. 超长序列治理 + assert 根治（§28，07-28~29）

真实训练跑到 step 16（2h）崩：某次 sandbox tool 输出巨量 → 整条 response 冲到 **319663 token** →
撞 verl `rearrange_micro_batches` 的 assert，整训练 rc=1。

- **原则**（用户定）：正式训练不该被调试 assert 崩，超长应丢弃/截断
- **三层截断**让 verl 永远收不到超标序列（assert 结构上不触发）：① 单次 tool 输出 ≤ 4096；
  ② rollout 整条 response 最终硬截断到 8192；③ 进 verl 前 trajectories_to_dataproto 再硬截断
- 单测验证：5 万 token 巨型输出 + 319663 超长，两层都截到 8192，且 resp_ids==response_mask 恒成立（不引入对齐漏洞）

## 5. logprob 未请求致 PPO clip 失效（§29，07-29）

首次真实训练 16 step，`actor/ppo_kl` 与 `pg_clipfrac` 全程 0。源码定位根因：

- verl lightllm client 从 `sampling_params.pop("logprobs", False)` 读是否返回 logprob，**默认 False**；
  我们只传 {temperature, max_tokens} → rollout 不带回 old_log_prob → verl 用当前策略重算 → old==new →
  ratio=1 → ppo_kl/clipfrac=0，**PPO 信任域裁剪实际失效**（退化 vanilla PG）
- 修：sampling_params 加 `"logprobs": True`（server 里 token_id 与 logprob 同循环 append，天然对齐）
- 澄清概念：`ppo_kl`（新 vs rollout旧策略，不用 ref）≠ `kl_loss`（ref-KL，K 系列才有）；baseline 不加载
  ref 是对的，ppo_kl=0 与 ref 无关
