## 整体思路

经过长期讨论，持续学习与RL的方案结论如下：

我们的离线强化学习训练的模型很厉害——这是因为有 8 路并行、GRPO group 的 winner、advantage 信号的富信息量。但在实际部署的时候，模型将面临陌生的场景和新的任务。

在这个时候需要一个**持续学习的机制**，虽然只是让模型做**不遗忘**的一步操作，但也足以让模型保持长久的基础能力，最差也只是在某个陌生领域不提升，不影响旧能力的退化。

也就是说，**并不是线上不训练，只是线上需要一个 CL 的机制，这个机制不要求做到极致、复杂的极高性能的优化，只需要在已有的绝大多数任务上，不会遗忘**。

所以天然的形成了一个二级的「学习结构」：
- **一级 RL**：离线 8 路强化学习，负责训练核心引擎
- **二级 CL**：线上持续学习防遗忘，负责保鲜

郑乃榕说：这不就是一个简单的 RL 训练 Loop 吗？

实际上确实也是这样——所以可以抽象为"对于一个给定模型，对不同来源（离线/线上）的数据，使用不同的策略进行学习"。

经过沟通，我理解了天阔之前为什么对 RL 抱有疑问：是因为他把持续学习的过程也当成了 RL 的一种形式。他认为 RL 就是"跑一条轨迹、打分、更新权重"——而 CL 是一个不同任务的训练循环（也就是 RewardLoop）。

在了解到我的想法后，天阔觉得这个方案可以作为一个「探索方向」。因为 RL 本身带有创新性，如果在持续学习中把 RL 单纯当做一个打分然后离线训练的数据生成器，那 RL 太"大材小用"。

最终我们达成一致：**RL 是核心引擎，CL 是保鲜手段**。

## 技术方案

### 1. 两个方案

1. 离线侧（一级 RL）：用 8 路采集、winner 机制、GRPO group 充分发挥 RL 的优势；也是我们之前在 `trainer/` 和 `verl` 的集成思路
2. 线上侧（二级 CL）：收到一条 query 后，在沙箱执行，judge 打分，将其轨迹存到 buffer 中；训练时使用 loss 中的 $L_{replay}$ （BC 的方式）防止遗忘

### 2. 核心思路

天阔倾向于使用简单的 RL 训练循环来实现持续学习的形式：离线可以是对着离线数据集训练，线上可以对着实时数据进行训练——就像是训练的过程（因为持续学习本来就只是另一个 trainer）。

但是我目前还是坚持 CL 的形式应该是 前几个月的方案——loss 的修改（CL 就是在 RL 的 loss 上加入了 $L_{replay}$, $L_{kl}$, $L_{ent}$），这样正好契合了"对于不同来源的数据，用不同的策略进行学习"的一个理念。

我们后续会继续讨论。

### 3. 当前要做的

1. 尽快部署上线：把现有代码打包成一个 docker 镜像，能够暴露一个可以调用的 API 接口 → 部署上线服务 → 跑一个月，采集首批轨迹，用这些数据看看能不能训
   - 好处：很快；验证 CL 有没有用；镜像部署后线上采集数据成本低；如果真的没用就不会浪费时间准备 GPU 和线上集群资源
2. 给郑乃榕提供一个镜像或服务，确认训练出来的模型能否使用
3. 根据线上采集的轨迹看 RL 训不训得了，然后正式考虑把 CL 模块接到线上 RL 训练 -> 持续校验
4. 需要进一步讨论：observer / questioner 是否是一个完全必要的模块？为了简化多轮数据采集，第一次上线真的有必要直接上多轮吗？单轮行不行？

### 4. Q1：先追上线

郑乃榕提到，持续学习可以把 observer/questioner（多轮 query 在线生成）先砍掉——因为我们现在的数据是：
1. 重建了 task
2. 已经有任务集群

直接把已有的任务集群用上，先搞定上线，后续再考虑 observer/questioner 的 multi-turn。这个我们可以继续单独讨论。
