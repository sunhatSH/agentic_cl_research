# 集群 GPU 推理/采集 — 踩坑与经验复盘

> **用途**：复用 + 面试讲解，**不进论文**。记录在商汤 SenseCore（8 机×8 卡 H800）上把 Qwen3.6-27B 跑起来做多轮 rollout 采集的全过程踩坑、流程、经验。
> **日期**：2026-06-13。配套：运行手册 `ColdRollout_采集.md`、系统报告 `RolloutCollect_技术报告.md`。

---

## 一、整体流程（从拿到集群到跑起来）

```
申请集群(8机×8卡, 平台侧) → 进节点 → 连通(SSH跳板/免密) → 凑环境 → 起vllm(每机TP=8) → 多机分片采集
```

1. **申请**：商汤平台网页提交，分到 8 台 Pod（对等 worker，无天生 master）。
2. **连通**：本地 Mac → 开发机(跳板) → 训练机，用 ProxyJump；集群内 8 机互相 SSH 免密。
3. **环境**：定位能加载模型架构的 python（最大坑，见三）。
4. **推理服务**：每台起 1 个本地 vllm（TP=8，单机 8 卡），暴露 OpenAI 兼容 endpoint。
5. **采集**：8 机共享盘一份代码/模型，ssh 下发，每机各跑 1/8 分片（取模切分），吞吐 ×8。

> 关键认知：**不是组跨机 Ray 起一个大模型**——27B dense 单机 8 卡足够；多机=各跑一份各采一份，简单且无跨机故障域。

## 二、连通：SSH 跳板机（ProxyJump）

### 方案
```
Mac ──ssh──> 开发机(跳板) ──ProxyJump──> 训练机
 └────────── 用同一把密钥端到端认证训练机 ──────────┘
```
**核心认知**：跳板机只转发 TCP、不登录训练机；真正登录训练机的是 Mac，用 Mac 的密钥端到端直连。所以：
- 开发机(跳板) **零配置**，不需要在它上面放任何公钥/私钥。
- 需放进训练机 `authorized_keys` 的是 **Mac 的公钥**。

### Mac 端 `~/.ssh/config`
```
Host cci_train
    HostName 10.120.5.53                   # 训练机「实例 IP」(10.120.x)，不是 Host IP(10.123.x)
    User root
    Port 22
    IdentityFile ~/.ssh/id_rsa
    ProxyJump cci_for_cl_loss_research_dev # 跳板机别名(开发机)
    StrictHostKeyChecking no               # 训练机常重建、指纹会变
    UserKnownHostsFile /dev/null
```

### 训练机启动脚本（root 执行，把 sshd 拉起来）
```bash
apt-get update && apt-get install -y openssh-server
mkdir -p /run/sshd
sed -i 's/^#*PermitRootLogin.*/PermitRootLogin prohibit-password/' /etc/ssh/sshd_config
mkdir -p /root/.ssh && chmod 700 /root/.ssh
cat > /root/.ssh/authorized_keys <<'EOF'
<粘贴 Mac 上 cat ~/.ssh/id_rsa.pub 的完整一行，含结尾 comment>
EOF
chmod 600 /root/.ssh/authorized_keys
chown -R root:root /root/.ssh
service ssh start
sleep 48h    # 吊住容器，否则跑完即停、sshd 也没了
```

### 选哪台当跳板终点
- 8 台 Pod 对等、无天生 master；rank0 是训练框架启动时才约定的，容器仅 sleep 挂着时 `RANK` 为空属正常。
- 终点选哪台都行（同内网互通）；习惯选实例名末尾 0 那台。
- **IP 用「实例 IP」(10.120.x.x)，不是「Host IP」(10.123.104.x)** —— sshd 跑在 Pod 里，Host IP 是物理机。

## 三、权限：SSH 密钥 / 公钥

### 私钥权限（集群内 8 机免密时踩到）
- 现象：`Permissions 0644 for id_rsa are too open ... This private key will be ignored` → 直接被拒、回退要密码。
- 修复：`chmod 600 ~/.ssh/id_rsa ~/.ssh/id_ed25519`。私钥**必须 600**，否则 ssh 静默忽略它。

权限正确（700 目录 / 600 文件 / root:root）时，改 `authorized_keys` **实时生效，无需重启 sshd**。

## 四、排错：看报错措辞分方向（通用，极有用）

| 报错 | 含义 | 方向 |
|------|------|------|
| `Connection timed out` | 网络不通 | 网段/防火墙隔离 |
| `Connection refused` | 网络通了，但该端口没 sshd 监听 | 训练机 sshd 没起 / 选错 IP（用了 Host IP） |
| `Permission denied` | sshd 在，但拒绝认证 | 公钥不匹配 / 权限错 |
| 问你要密码（且 `prohibit-password`） | 密钥被拒回退密码又被禁 → 卡死 | 公钥问题（不是 PermitRootLogin 错） |

> 同理迁移到 vllm/服务端口：`curl :8000/v1/models` 报 `Connection refused` = 服务没起/还在加载，不是网络问题。

## 五、环境凑齐：能加载 Qwen3.6-27B 的 vllm（最大技术坑）

Qwen3.6-27B 的**架构是 `qwen3_5`（attention+mamba 混合）**，对 vllm/transformers 版本有硬要求。踩了一圈：

| 尝试 | 结果 |
|------|------|
| `/opt/conda`：vllm0.11 + torch2.9.1 | ❌ ABI 不匹配（`vllm._C undefined symbol`）；且 vllm0.11/0.13 **没有 `qwen3_5.py`**，根本不支持该架构 |
| vllm0.13 overlay + transformers5.2 | ❌ 死结：vllm0.13 要 `transformers<5`，但 `qwen3_5` 需 transformers≥5.2（`ALLOWED_LAYER_TYPES` import 失败） |
| **`/mnt/afs_code/ds32_env`：vllm0.16rc** | ✅ **唯一可用**：自带 `qwen3_5.py` 建模，`Resolved architecture: Qwen3_5ForConditionalGeneration` |

**经验**：
1. **新模型架构看 vllm 是否自带建模文件**：`ls .../vllm/model_executor/models/ | grep <arch>`，没有就是不支持，换 vllm 版本，别在旧 vllm 上硬凑 transformers。
2. **`model_type`(架构) ≠ 模型版本号**：Qwen3.6 的 `model_type=qwen3_5`，加载的仍是 3.6 权重——别被架构代号误导。
3. vllm `--no-deps --target` 装到 quarkfs 共享盘会因 `rmtree` 非空目录失败（FUSE bug）；且会缺运行时依赖（`model_hosting_container_standards` 等）。**别凑，直接找配套环境**。

## 六、进程稳定性：用 tmux，别用 nohup

- 现象：这台机器上 `nohup ... &` 起的 vllm 反复被 SIGTERM 中断（exit 143/144），加载到一半就 `Shutting down`。
- **修复：长进程一律在 tmux 里跑**（`tmux new-session -d -s vllm "..."`），进程独立于 ssh 连接和调用方，不被中断。
- 监控用 `tail -f 日志` + `curl /v1/models`，不要 attach 干扰。

---

## 七、27B 加载慢（quarkfs IO）

- 27B（~54GB，15 分片）在 quarkfs 共享盘加载 **~15–20 分钟**（越往后越慢，~100s/分片），是共享盘 IO 限速，一次性成本。
- 判断就绪：`curl :8000/v1/models` 返回含 served-model-name 的 JSON；日志出现 `Application startup complete`。
- 加载阶段 GPU 显存逐步上升（init→NCCL→权重→CUDA graph→KV cache），全程约 15 分钟。

## 七点五、★flashinfer JIT 缓存在 quarkfs → flock 崩溃（8 机崩溃 + GPU 0% 真根因）

> **真根因已定位并验证修复（2026-06-13）**：不是 vllm/triton 缓存，而是 **flashinfer JIT**。Qwen3.6(`qwen3_5`,含 mamba/gated-delta-rule)首次推理时 flashinfer 编译 `gdn_prefill` kernel，其 `FileLock(fcntl.flock)` 缓存默认在 `HOME/.cache/flashinfer`（quarkfs/FUSE）→ flock 锁文件 `FileNotFoundError` → worker 崩 → vllm shutdown → GPU 0% → 采集空跑。
> traceback 链：`qwen3_next.gdn_attention_core → flashinfer/gdn_prefill.py → flashinfer/jit/core.py:314 FileLock → fcntl.flock FileNotFoundError`。
> **修复（验证 flock 错误归零、压测不崩、推理非空）**：`export FLASHINFER_WORKSPACE_BASE=/tmp/...`（控制变量是 `_BASE`，**不是** `FLASHINFER_WORKSPACE_DIR`）。验证：`FLASHINFER_WORKSPACE_BASE=/tmp/x python -c "from flashinfer.jit import env as e;print(e.FLASHINFER_WORKSPACE_DIR)"` 应显示 `/tmp/x/...`。
> 排查教训：看 traceback **最内层文件路径**定位（是 flashinfer 不是 vllm/triton），别凭猜设缓存 env——先设 VLLM_CACHE_ROOT/TRITON_CACHE_DIR 仍崩就是因为猜错了模块。
> **GPU 0% 排查口诀**：GPU 利用率是"推理是否真发生"的最硬指标，比采集进度数字可靠。0% → 先 `curl :8000/v1/models`(refused=vllm死) → `grep -iE 'shutting down|flock|FileNotFoundError|ninja' logs/cold/vllm_*.log` 找真因 → 抽查轨迹 assistant 是否空。
> **次要坑 ninja**：`export PATH=$(dirname $PY):$PATH`（编译子进程调命令行 ninja 走 PATH）。
> **为何 smoke 没暴露**：limit=2 没触发 gdn kernel 首次 JIT；8 机大量请求才触发 → 小批过≠大规模稳，长稳必压测。

## （以下为初次排查时的弯路记录，根因以上方为准）★vllm 缓存在 quarkfs → filelock 崩溃

**现象**：8 机 vllm 起来后能服务一阵，推理若干请求后**集体 `Shutting down`**，GPU 掉回 0%。日志关键行：
```
ERROR multiproc_executor.py:863 ... filelock/_unix.py ... fcntl.flock(fd, fcntl.LOCK_UN)
FileNotFoundError: [Errno 2] No such file or directory
WorkerProc shutting down.
```
（同时还有 `FileNotFoundError: 'ninja'`，但那是次要——见下。）

**根因**：`HOME=/mnt/afs_toolcall/sunhao4` 在 **quarkfs(FUSE)**，vllm/triton 即时编译 kernel 的缓存与**锁文件**默认落在 `~/.cache/vllm`、`~/.triton`。FUSE 上 `fcntl.flock` / 锁文件操作**不可靠**（锁文件会"消失"→ FileNotFoundError），worker 崩 → vllm 连锁 shutdown。**与 `pip --target` 在 quarkfs 上 `rmtree` 失败是同一类 FUSE 问题。**

**修复**：所有编译/缓存目录指到**本地盘**（overlay 的 `/tmp`，**不是** `/root`——非 root 用户无权限）：
```bash
export VLLM_CACHE_ROOT=/tmp/vcache_r${RANK}/vllm
export TRITON_CACHE_DIR=/tmp/vcache_r${RANK}/triton
export TORCHINDUCTOR_CACHE_DIR=/tmp/vcache_r${RANK}/inductor
export XDG_CACHE_HOME=/tmp/vcache_r${RANK}/xdg   # 兜底其余 ~/.cache 使用者
```
每机用 `_r${RANK}` 隔离避免互踩。`/tmp` 是 overlay 本地盘（`df /tmp` 见 overlay，非 quarkfs）。

**次要坑：`ninja` 不在 PATH**。用绝对路径 `ds32_env/bin/python` 起 vllm，但编译时子进程调命令行 `ninja` 走 PATH，PATH 里没 `ds32_env/bin` → `FileNotFoundError: 'ninja'`。修：`export PATH=$(dirname $PY):$PATH`。（`ninja` 可执行其实自带在 `ds32_env/bin/ninja`，只是没进 PATH。）

> **为何 smoke（limit=2）没暴露**：少量请求没触发到坏的编译/锁路径；8 机大量并发请求才触发 → **小批验证过≠大规模稳**，长稳必须压测。

## 七点六、★采集对 actor 不可用不 fail-fast → 空跑产垃圾（最隐蔽）

**现象**：vllm 已崩、GPU 0%，但采集脚本 `done=` 计数照常上涨（done=380…），产出几百条 `{"role":"assistant","content":""}` 的**空轨迹**，完全无感知。一度误判"8 机正常在跑"。

**根因**：actor endpoint 挂掉后，`HTTPGenerateFn` 的异常在上层 ReAct/session 循环被吞 → 返回空 `GenStep` → 轨迹空但 session 计为 done。**没有"actor 不可用就停"的 fail-fast。**

**修复**：`collect_rollout.py` 启动时**先 ping actor**——打一个真实请求，空/不通直接 `sys.exit(6)`：
```python
probe = generate_fn([{"role":"user","content":"ping"}])
if not (probe.text or "").strip(): sys.exit(6)   # endpoint up but model dead
```
**教训**：`done` 计数会骗人；判断采集真在产数据要**抽查轨迹 assistant 是否非空 + 看 GPU 利用率**，不能只看进度数字。GPU 利用率 0% + 采集"在跑" = 必定空跑。

## 七点七、判断"采集真在干活"的体检清单

止血/排查时按此快速判定：
```bash
curl :8000/v1/models                      # endpoint 活？
nvidia-smi --query-gpu=utilization.gpu... # 利用率 >0？(0% = 空转)
# 抽查最新轨迹 assistant 是否非空：
python -c "import json;r=[json.loads(l) for l in open('<out>.jsonl')];print(repr(r[-1]['trajectories'][0]['messages']))"
grep -iE 'shutting down|FileNotFoundError|ninja|flock' logs/cold/vllm_r*.log
```

## 八、多机分片采集（8 机不重复）

- 共享盘 `/mnt/afs_toolcall` 8 机共用 → 代码/模型一份即可，无需每台装。
- 分片：`--node-rank i --num-nodes 8`，种子按 `idx % 8 == rank` 取模切分（已验证 8 片覆盖全集、不重不漏）。
- 输出文件带 rank 后缀（`rollouts_local_r{i}.jsonl`），避免 8 机抢写同一文件。
- 下发：rank0 本地起 + ssh 到 7 peers 起（均在各自 tmux 内），日志/产物落共享盘各机分开。

## 九、一句话面试版

> 在 8 机×8 卡 H800 集群上部署 27B（mamba 混合架构）做多轮 agentic rollout 采集。难点三层：**连通**（ProxyJump 跳板 + 端到端密钥认证，按报错措辞 timeout/refused/denied 分方向定位）、**环境**（新架构只有特定 vllm 版本支持，靠查 `model_executor/models/` 建模文件定位，不在旧版上硬凑依赖）、**稳定性与规模**（长进程用 tmux 抗中断；8 机共享盘 + 取模分片，单机各跑一份 27B 各采 1/8，吞吐线性扩展，无跨机故障域）。
