# Continual Learning Replay Buffer 桶结构设计

## 速查

> 以下为本设计的结论摘要，详细论证见后续各节。

1. **按能力/领域分桶**，不按难度分桶（难度会漂移）
2. **每桶保底配额**，防高频任务挤空低频桶
3. **桶内淘汰**，禁止跨桶挤出
4. **Priority 不用 reward 绝对值**（reward 整体上升会系统性淘汰旧轨迹，buffer 退化为滑动窗口）

7 桶 = Workflow[54] / SysOps[52] / Dialogue[38] / Finance[18] / Communication[12] / Knowledge[11] / OfficeQA[10]（OfficeQA 单独成桶，不并入 Knowledge；不纳入 multimodal）

Quota：$q_i = q_{min} + (C - B\cdot q_{min})\cdot n_i^{0.5}/\sum_j n_j^{0.5}$（25k 示例：Workflow≈4319 → OfficeQA≈2995）

Priority = forgetting_risk(0.5) + rarity(0.25) + difficulty(0.25)（v1 diversity 禁用）

采样：两级（采桶=比例+均匀混合 → 桶内=priority 加权随机，非 top-k）

**一句话**：能力分桶保覆盖 → 保底 quota 防挤空 → 抗遗忘 priority 保质量 → 桶内淘汰防侵占 → 两级采样保有效性

---

## 目标

本设计的目标是在模型持续学习新任务时，尽量避免遗忘旧任务能力。由于遗忘通常表现为某一类能力整体退化，而不是单纯丢失若干高 reward 样本，因此 Replay Buffer 的设计应优先服务于“能力保持”，而不是服务于“保留历史最高 reward 轨迹”。

当前方案仅针对纯文本任务，不包含 multimodal 任务。

---

## 一、设计原则

1. **不按难度分桶**
   难度会随模型能力提升而漂移，不是稳定的分桶依据；而灾难性遗忘更常沿能力类型发生。

2. **按能力/领域分桶**
   同一能力类型中的简单样本与困难样本应放在同一桶内，通过桶内优先级机制区分保留价值。

3. **每个桶有保底配额**
   避免高频任务类型长期挤压低频但重要的旧能力，保证各类能力始终存在 replay 机会。

4. **桶内按 priority 存留，桶间不直接竞争**
   新轨迹只与所属桶中的已有轨迹竞争，不做全局统一淘汰。这样可以避免热门任务不断吞噬其他能力类型的容量。

5. **priority 不依赖 reward 绝对值**
   训练过程中 reward 通常整体上升，若直接按 reward 排序，旧轨迹会因“年代久远”而系统性被淘汰，最终使 buffer 退化为滑动窗口。

---

## 二、为什么采用“能力分桶 + 保底 quota + 桶内防遗忘 priority”

本问题的核心不是简单保存旧数据，而是让模型在学习新任务时持续暴露于旧能力对应的代表性轨迹。为此，Replay Buffer 需要同时解决两个层面的遗忘问题：

- **跨能力遗忘**：某些任务类型因为近期训练频率较低，被新任务整体挤出 buffer。
- **桶内退化**：即使某类能力仍有桶存在，桶内也可能只剩最近的、重复的、短期高 reward 轨迹，失去对旧能力的代表性。

因此，推荐采用以下总体方案：

**能力分桶 + 每桶保底配额 + 桶内基于遗忘风险的 priority + 两级采样**

这个方案的优势在于：

- 从结构上保护能力覆盖；
- 从桶内机制上保护高价值旧轨迹；
- 计算代价可控，适合在每个 RL step 中进行更新与采样；
- 能避免 buffer 退化为只记住最近任务的滑动窗口。

## 四、为什么不纳入 multimodal

当前目标是纯文本 continual learning，因此 General split 中的 multimodal (4) 不进入本次 Replay Buffer 桶设计。

原因如下：

1. **目标不一致**
   当前评测和训练目标都聚焦纯文本，multimodal 的引入会混入额外模态差异，影响桶的能力边界定义。

2. **数据量太小**
   multimodal 仅 4 个任务，单独成桶会造成极小桶；硬并入文本桶又会削弱分桶语义一致性。

3. **能力结构不同**
   multimodal 任务的输入分布、表示结构和错误模式与纯文本任务不同，不应在当前阶段混入文本 replay 机制。

因此，本设计中纯文本 buffer 总任务数按 195 计算，即 199 个纯文本相关任务中剔除 4 个 multimodal。

---

## 五、为什么 OfficeQA 需要单独成桶

尽管 office_qa 只有 10 个任务，但仍建议单独设桶，原因如下：

1. **高内聚能力簇**
   OfficeQA 不是泛化的知识问答，而是更偏向办公语境中的结构化问答、字段定位、文档细节理解与办公信息处理。

2. **并入 Knowledge/Analysis 后容易被稀释**
   如果与 research、knowledge、synthesis 等合并，office_qa 在 replay 中会被更泛的理解与总结类样本覆盖，降低其作为独立能力被保留的概率。

3. **保底 quota 的收益高于额外复杂度**
   在 10k–50k buffer 容量范围内，多保留一个桶的工程成本很低，但能显著提高对办公场景能力的抗遗忘稳定性。

因此，本方案中 OfficeQA 单独成桶是合理且推荐的选择。

## 六、Quota 分配策略

### 6.1 不采用纯比例分配

如果完全按任务数比例分配，Workflow、SysOps、Dialogue 会占据过大空间，而 Finance、OfficeQA、Communication、Knowledge/Analysis 等中小桶将只有很少容量。这样虽然接近原始 benchmark 分布，但不利于防遗忘，因为低频能力会在持续训练中长期得不到 replay。

### 6.2 不采用完全均匀分配

如果所有桶均分容量，则无法反映不同桶的覆盖需求。Workflow 和 SysOps 这类大桶内部任务类型更丰富，若与 OfficeQA 获得相同空间，会导致大桶覆盖不足、竞争过强。

### 6.3 推荐：保底 + 次线性加权分配

推荐为每个桶设置最低保底配额，在此基础上将剩余容量按桶大小做次线性加权分配。一个合适的形式为：

\[
q_i = q_{min} + (C - B q_{min}) \cdot \frac{n_i^\alpha}{\sum_j n_j^\alpha}
\]

其中：

- \(C\)：总 buffer 容量
- \(B\)：桶数
- \(q_{min}\)：每桶保底配额
- \(n_i\)：第 \(i\) 个桶对应的任务数
- \(\alpha\)：次线性指数，建议取 0.5–0.7

推荐优先使用 **平方根分配**，即 \(\alpha = 0.5\)。

其含义是：

- 大桶比小桶拥有更多容量；
- 但容量增长慢于任务数增长；
- 因而能同时照顾主流能力和长尾能力。

### 6.4 Quota 的具体公式

设：

- \(C\)：Buffer 总容量（当前建议以轨迹条数计）
- \(B\)：桶数，本设计中 \(B = 7\)
- \(n_i\)：第 \(i\) 个桶对应的任务数
- \(q_i\)：第 \(i\) 个桶的目标 quota
- \(q_{min}\)：每桶 hard floor
- \(\alpha\)：次线性指数，推荐取 \(0.5\)

则 quota 定义为：

\[
q_i = q_{min} + (C - B q_{min}) \cdot \frac{n_i^\alpha}{\sum_j n_j^\alpha}
\]

其中：

- 第一项 \(q_{min}\) 保证每个桶都有最低生存空间；
- 第二项把剩余容量按桶规模做次线性分配；
- 当 \(\alpha = 0.5\) 时，相当于按平方根加权，能兼顾大桶覆盖需求与小桶抗遗忘需求。

### 6.5 一个具体示例：总容量 25k trajectories

若总容量取 \(C = 25{,}000\)，并设每桶 hard floor 为 \(q_{min} = 2{,}000\)，则：

- 总 hard floor 为 \(7 \times 2{,}000 = 14{,}000\)
- 剩余可分配容量为 \(25{,}000 - 14{,}000 = 11{,}000\)

7 个桶的任务数分别为：

- Workflow = 54
- SysOps = 52
- Finance = 18
- Knowledge/Analysis = 11
- Communication = 12
- OfficeQA = 10
- Dialogue = 38

当 \(\alpha = 0.5\) 时，各桶权重约为：

- Workflow: \(\sqrt{54} \approx 7.35\)
- SysOps: \(\sqrt{52} \approx 7.21\)
- Finance: \(\sqrt{18} \approx 4.24\)
- Knowledge/Analysis: \(\sqrt{11} \approx 3.32\)
- Communication: \(\sqrt{12} \approx 3.46\)
- OfficeQA: \(\sqrt{10} \approx 3.16\)
- Dialogue: \(\sqrt{38} \approx 6.16\)

权重总和约为：

\[
7.35 + 7.21 + 4.24 + 3.32 + 3.46 + 3.16 + 6.16 \approx 34.90
\]

据此可得到一组可落地的 quota 近似值：

| 桶 | 任务数 | quota 近似值 |
|---|---:|---:|
| Workflow | 54 | 4,319 |
| SysOps | 52 | 4,272 |
| Finance | 18 | 3,337 |
| Knowledge/Analysis | 11 | 3,047 |
| Communication | 12 | 3,092 |
| OfficeQA | 10 | 2,995 |
| Dialogue | 38 | 3,938 |

这些数值不要求在实现中逐条精确一致，但它们给出了一个非常清晰的配额量级：

- Workflow / SysOps / Dialogue 作为大桶，配额更高；
- Finance 居中；
- Knowledge/Analysis / Communication / OfficeQA 虽然任务数较少，但仍因 hard floor 和次线性加权得到足够容量；
- 这样可避免小桶在长期训练中被逐步挤空。

### 6.6 工程上的理解方式

可将 quota 分为两层：

- **hard floor**：每桶最低必须保留的容量；
- **soft target**：依据上式计算得到的目标容量。

更新时：

- 若桶容量低于 soft target，则新轨迹更容易被接纳；
- 若桶容量高于 soft target，则桶内淘汰更积极；
- 无论如何不应跌破 hard floor。

这种设计比刚性的“固定配额”更稳定，也更适合在线训练场景。

## 七、Priority 的设计原则

### 7.1 不使用 reward 绝对值

这是本设计中最关键的约束。原因在于，随着训练推进，模型在新数据上的 reward 往往整体上升。如果用 reward 绝对值决定保留优先级，则新轨迹会系统性压制旧轨迹，导致旧任务样本持续流失，最终 buffer 变成“最近任务缓存”，失去 continual learning 的意义。

因此，priority 必须反映的是：

**这条轨迹对防止遗忘有多重要**，而不是 **这条轨迹在当时取得了多高 reward**。

### 7.2 推荐的 priority 构成

桶内 priority 建议由以下几类信号组成：

1. **Forgetting Risk（遗忘风险）**
   反映当前模型在该轨迹上是否出现性能回退。若一条旧轨迹在 replay 时表现较历史最好水平明显变差，则说明它对抗遗忘的价值较高。

2. **Rarity（稀缺性）**
   在某桶内部，出现频率较低的模式、模板或任务子类应更难被淘汰，以防 buffer 被少数热门模板占满。

3. **Diversity / Redundancy（多样性 / 去重）**
   若桶内已有大量近似轨迹，则新轨迹的边际价值下降，应降低保留优先级。考虑到每个 query 只有 2 条轨迹，重复堆积的风险较高，因此该项尤其重要。

4. **Within-bucket Difficulty（桶内相对难度）**
   可保留一定难度信息，但只能使用桶内相对难度，而不是全局绝对 reward。它刻画的是：在同一能力类型内部，哪些轨迹更能代表边界情况、复杂流程或高约束场景。

### 7.3 推荐的理解方式

可将 priority 理解为一条轨迹的“抗遗忘价值”。高 priority 轨迹不一定是历史 reward 最高的轨迹，而是那些能够：

- 代表某种旧能力；
- 当前已出现退化迹象；
- 在桶内较少见；
- 与其他样本不重复；
- 能覆盖该能力的关键边界场景。

---

## 八、为什么必须采用桶内淘汰

若使用全局淘汰机制，则所有轨迹不分桶直接竞争，会导致高频任务类型持续吞噬其他类型的容量。最终即便引入分桶，也只是“名义上分桶”，无法真正保护不同能力的长期存在。

因此，本设计明确要求：

- 新轨迹先根据能力映射进入所属桶；
- 若该桶未满，则直接接纳；
- 若该桶已满，则只在该桶内部比较并淘汰低价值轨迹；
- 不允许新任务跨桶挤出旧任务。

这一步是保证 replay buffer 真正服务于能力保持的关键。

---

## 九、采样策略

为了使 buffer 中被保留的轨迹真正参与训练，采样策略也应与分桶结构一致。推荐采用两级采样：

### 9.1 第一级：先采桶

桶采样不应完全按桶容量比例进行，否则中小桶会长期欠采样。也不宜完全均匀，否则会过度偏向小桶。

推荐采用混合策略：

- 一部分概率按桶 quota 或 soft target 比例采样；
- 一部分概率按桶均匀采样。

这样既能保证大桶的覆盖需求，又能保证长尾能力持续被 replay。

### 9.2 第二级：桶内采轨迹

在选中桶后，再按桶内 priority 进行轨迹采样。这里不建议总是贪心选 top 样本，而应采用带随机性的 priority 采样方式，以避免桶内只重复使用少数“明星轨迹”，损害覆盖度。

因此，采样机制应强调：

- 先保证能力覆盖；
- 再在能力内部偏向高抗遗忘价值样本；
- 同时保留一定探索性。

---

## 十、与目标的对应关系

本设计直接服务于如下目标：

**当模型学习新任务时，不忘记旧任务的使用能力。**

对应关系如下：

- **按能力分桶**：保证旧能力在结构上不会整体消失；
- **每桶保底 quota**：保证低频但重要的旧能力始终有生存空间；
- **桶内 priority 不依赖 reward 绝对值**：防止旧样本因时间原因被系统性清除；
- **桶内淘汰**：防止高频新任务跨桶挤压旧能力；
- **两级采样**：保证保留下来的旧能力轨迹能够持续参与训练。

因此，如果目标是“学新不忘旧”，那么相较于 reward-based replay，本方案更适合作为 Continual Learning 的 Replay Buffer 结构。

---

## 十一、Buffer 中轨迹的作用

Replay Buffer 中的轨迹不是历史日志，也不是用于推理时直接塞入上下文的长记忆材料。它们的核心作用是：在训练新任务时，持续作为旧任务能力的代表样本被 replay，从而防止模型遗忘旧能力。

具体而言，Buffer 中轨迹承担以下职责：

1. **作为旧能力的训练锚点**
   模型不会自动记住过去学会的能力，必须依靠具体轨迹在后续训练中反复出现，才能维持这些能力对应的参数区域。

2. **维持旧任务分布的可见性**
   当训练流被新任务主导时，旧轨迹通过 replay 重新进入训练分布，防止模型参数持续向新任务单边漂移。

3. **保留代表性模式与边界情况**
   Buffer 不是为了保存所有历史，而是为了保留对旧能力最有代表性的子集，包括典型模式、稀有模式和容易遗忘的边界案例。

4. **为训练提供软约束**
   replay 的存在相当于告诉模型：可以继续学习新任务，但不能以明显损伤旧任务能力为代价。

因此，Buffer 里的轨迹价值不在于它曾经获得多高 reward，而在于它是否能有效帮助模型维持某类旧能力。

---

## 十二、训练新任务时，Replay 的对象是什么

在训练某个新任务时，被 replay 的不是 Buffer 里的所有轨迹，也不是所有旧任务的全集，而是从 Buffer 中按既定策略采样出来的一小部分旧轨迹。

这些被 replay 的轨迹应当满足以下目标之一：

1. **代表各能力桶的核心模式**
   保证旧能力整体仍然可见，而不是长期只训练新任务。

2. **覆盖稀缺但重要的模式**
   防止长尾能力、少见模板或边界情况长期得不到 replay。

3. **优先选择出现遗忘迹象的轨迹**
   如果某条旧轨迹在最近 replay 中表现下降，则应提高它再次被采样的概率。

4. **补偿长期未被覆盖的代表样本**
   防止某些轨迹虽然仍在 Buffer 中，但实际上长期没有参与训练。

因此，Replay 的对象不应理解为“全部旧任务”，也不应简化为“只取和当前新任务最相似的旧任务”，而应理解为：

**从各个能力桶中按抗遗忘价值采样出的旧能力代表样本子集。**

---

## 十三、为什么即使单步只 Replay 少量轨迹，仍然需要淘汰机制

即使每个训练 step 只从 Buffer 中取出极少量轨迹，例如 1 条或几条，也仍然需要淘汰机制。原因在于，淘汰解决的不是“单步读取量”，而是“长期存储集合的质量”。

具体原因如下：

1. **存储预算不是无限的**
   训练过程中轨迹会持续进入 Buffer。如果不淘汰，历史轨迹会不断累积，最终使 Buffer 变成无限增长的日志集合，不再是一个受控的 replay 结构。

2. **不是所有轨迹都同样有价值**
   很多旧轨迹可能高度重复、过于简单、质量较低，或已经不再具有代表性。如果全部保留，会降低被采样轨迹的平均抗遗忘价值。

3. **不淘汰会让高价值样本被稀释**
   即使每次只采 1 条，如果候选池无限膨胀，那么真正关键的旧轨迹在长期中被抽中的概率会越来越低。结果是 replay 仍然存在，但实际上难以有效命中重要样本。

4. **不淘汰会破坏桶内代表性**
   高频模式会随着时间不断堆积，占据越来越大比例；稀有模式虽然名义上仍在 Buffer 中，但会被埋没在大量低价值重复样本里。

因此，淘汰机制的作用不是简单节省空间，而是把 Buffer 维持为一个固定预算下的高密度代表集，使未来每一次 replay 都更可能命中真正有价值的旧能力样本。

## 十四、Buffer 内容的组织与精确检索原则

为了让 Buffer 不仅能用于训练采样，也能支持分析、调试和定向 replay，系统需要具备“精确取出”轨迹的能力。这里的“精确取出”不是指随机采样技巧，而是指：在已知目标条件下，可以稳定地取出符合要求的轨迹集合。

### 14.1 精确取出的前提：轨迹级元数据

每条轨迹至少应维护以下元数据：

- `trajectory_id`
- `bucket`
- `source_task` 或 `source_category`
- `priority`
- `insert_step`
- `last_replay_step`
- `replay_count`
- `token_length`
- `pattern_id` / `template_id`（如果可获得）
- 与遗忘相关的状态标记，例如是否近期出现性能回退、是否属于稀有模式、是否属于边界样本

这些字段的作用不是增加复杂度，而是为后续检索、分析和可控采样提供最基本的结构支撑。

### 14.2 应采用“主存储 + 轻量索引”的组织方式

Buffer 不应只是一个简单数组或链表，而应理解为：

- 一份保存轨迹本体的主存储；
- 若干个面向常见查询需求的轻量索引结构。

至少应支持以下索引视角：

1. **按 ID 访问**
   用于精确复查某条轨迹。

2. **按 bucket 访问**
   用于分析某个能力桶中实际保留了什么内容。

3. **按 priority 排序访问**
   用于查看某桶中最该保留和最该淘汰的轨迹。

4. **按 pattern / template / task family 访问**
   用于检查重复堆积、稀有模式覆盖和子类能力分布。

### 14.3 精确取出与训练采样应区分开

需要明确区分两类操作：

1. **精确查询（deterministic retrieval）**
   给定明确条件后，返回满足条件的轨迹集合。其主要作用是调试、诊断、评估和人工分析。

2. **训练采样（stochastic replay sampling）**
   在候选集合上按某种概率规则进行抽样。其主要作用是训练。

也就是说，训练中的 replay 不应替代精确检索接口；反过来，精确检索接口也不等于训练采样。两者应在设计上分开。

### 14.4 第一版最值得支持的精确查询类型

在低开销前提下，第一版建议至少支持以下几类查询：

1. **查询某个 bucket 的全部轨迹**
   用于检查桶的内容与分布。

2. **查询某个 bucket 中 top-k / bottom-k priority 轨迹**
   用于验证 priority 与淘汰机制是否符合预期。

3. **查询长时间未被 replay 的轨迹**
   用于识别“名义上仍在 Buffer 中，但实际上已经失活”的样本。

4. **查询某个 pattern / task_id 对应的轨迹**
   用于检查是否存在过度重复，或某类模式是否覆盖不足。

精确取出的能力越完善，后续对 quota、priority、淘汰与采样策略的调试就越可控。

## 十五、最终结论

在当前“仅纯文本、不做多模态、追求低开销在线更新”的前提下，推荐采用如下方案：

### 桶结构
- Workflow = workflow + productivity
- SysOps = ops + operations + terminal + safety + security + file_ops + coding
- Finance = finance + compliance + procurement
- Knowledge/Analysis = research + knowledge + synthesis + comprehension + data_analysis + memory
- Communication = communication + content + rewriting + organization
- OfficeQA = office_qa
- Dialogue = what + user_agent

### 配额
采用 **每桶保底 + 按桶大小做次线性加权分配** 的方式，优先推荐平方根分配。

### Priority
采用 **面向抗遗忘的 priority**，重点考虑遗忘风险、稀缺性、多样性与桶内相对难度，不使用 reward 绝对值作为主要依据。

### 淘汰与采样
采用 **桶内淘汰 + 两级采样**，确保不同能力长期存在，并持续参与 replay。

### Buffer 组织与检索
采用 **轨迹级元数据 + 桶级组织 + 轻量索引** 的方式，使 Buffer 同时支持训练 replay 与精确内容分析。

这套设计在理论上贴合 continual learning 的抗遗忘目标，在工程上也满足 buffer 容量 10k–50k、每步在线更新与采样、计算成本可控的约束。
